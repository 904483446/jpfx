# V0.2 空间内文档管理设计

**日期：** 2026-07-15
**状态：** 已确认，待审阅设计文档

## 目标与范围

V0.2 在已登录用户自己的产品空间内提供文档上传、文档列表、状态展示和删除能力，为 V0.3 的文本解析、切片、embedding 与 RAG 建立安全的数据和存储边界。

本阶段交付：

- `documents` 数据表与 Alembic 迁移。
- PDF、DOCX、TXT、MD 的单文件上传、列表和删除。
- 单文件最大 20MB。
- 本地开发环境的受控文件存储。
- 文档状态标签：`uploaded`、`processing`、`indexed`、`failed`。
- 空间详情页升级为知识库文档管理页。

本阶段明确不做：

- 文本解析、OCR、文本切片、embedding、pgvector、RAG。
- 文档重新索引接口或按钮；待 V0.3 的真实索引流水线确定后再定义语义。
- 直接上传 Supabase Storage、签名 URL 或存储服务配置。
- 空间编辑/删除、前端退出登录、知识库详情展示及其他 V0.2+ 功能。

## 已有基线与约束

- 基线为 `origin/main` 的 `035469c`；实现只在 `feat/v0.2-document-management-design` worktree 中进行。
- 后端已有 `Space`、每空间一个 `KnowledgeBase`、当前用户依赖和统一中文错误响应。
- 前端 API Client 已固定使用 `credentials: "include"`；不得在浏览器保存或展示 JWT。
- 所有资源访问必须同时按当前用户与所属空间隔离；跨用户访问统一按资源不存在处理。
- 不读取、输出、提交或修改真实 `.env`、`.env.local`、密钥、Cookie、Token。

## 方案选择

采用“后端接收 multipart 文件 + 本地受控文件存储 + 数据库存储元数据”的方案。

后端承担空间归属校验、格式与大小校验、存储路径生成和数据库事务控制。文件不存入数据库二进制字段，也不由浏览器直传第三方存储服务。该方案可在不引入签名 URL、Supabase 凭据和额外权限模型的前提下完成 V0.2；后续通过存储提供者抽象切换到 Supabase Storage，而不改变文档业务接口。

## 数据模型与隔离

新增 `documents` 表，对应字段：

| 字段 | 规则 |
| --- | --- |
| `id` | UUID 主键 |
| `user_id` | 非空；关联 `users`，作为所有权边界 |
| `space_id` | 非空；与 `user_id` 共同关联所属 `spaces` |
| `knowledge_base_id` | 非空；关联该空间唯一的默认知识库 |
| `filename` | 用户可见的原始文件名；不作为磁盘路径 |
| `file_type` | 规范化扩展名：`pdf`、`docx`、`txt`、`md` |
| `file_size` | 正整数，单位字节 |
| `storage_path` | 服务端生成的相对安全路径，不在前端响应中暴露 |
| `status` | `uploaded`、`processing`、`indexed`、`failed` |
| `error_message` | 仅保存可面向用户的中文业务错误；V0.2 上传成功时为空 |
| `created_at` / `updated_at` | 统一时间戳 |

迁移使用复合外键约束，保证文档的空间和知识库与同一 `user_id` 相匹配。查询与删除均以当前用户为条件；空间内列表另以 `space_id` 过滤。请求其他用户或其他空间的文档时返回统一中文错误：

```json
{
  "error": {
    "code": "DOCUMENT_NOT_FOUND",
    "message": "文档不存在",
    "details": {}
  }
}
```

## 存储与状态机

本地文件放在 Git 忽略的受控 storage 根目录下。服务端为每次上传生成不可预测的内部文件名，并将其置于按用户和空间划分的目录中；原始文件名仅作为元数据保存。不得信任客户端提交的路径或文件名来决定存储位置。

上传校验顺序：先认证与空间所有权，再校验扩展名、非空内容和 20MB 限制，最后写入文件并创建文档记录。校验失败不应产生文件或数据库记录；文件写入与元数据持久化发生异常时清理已写入文件并回滚数据库事务。

V0.2 只写入 `uploaded`。前端可兼容显示完整状态枚举，但不会在本阶段把文档推进至 `processing`、`indexed` 或 `failed`。V0.3 增加真实解析与索引任务时负责以下迁移：`uploaded → processing → indexed`，或失败时进入 `failed` 并记录安全的中文原因。

删除按“删除元数据与存储文件”的语义执行。若存储文件已不存在，仍删除可访问的元数据，记录服务端诊断信息但不向用户返回内部路径或异常内容。

## API 设计

所有接口均位于现有 `/api/v1` 前缀，并使用 Cookie 会话鉴权。

| 接口 | 行为 |
| --- | --- |
| `POST /spaces/{space_id}/documents` | 接收单个 multipart 文件；校验、存储并创建状态为 `uploaded` 的文档记录；成功返回 201 |
| `GET /spaces/{space_id}/documents` | 返回当前用户在该空间内的文档列表，按创建时间倒序 |
| `DELETE /documents/{document_id}` | 仅删除当前用户可访问的文档；成功返回 204 |

响应模型只返回用户所需的 `id`、文件名、类型、大小、状态、错误消息和时间戳；不得返回 `user_id`、`knowledge_base_id`、`storage_path` 或服务器内部异常。

格式不支持、文件过大和空文件均采用既有统一中文错误包络；错误代码在实施计划中与现有 `core/errors` 命名规范一起确定。不得返回 HTML 错误页或直接暴露底层异常。

## 前端设计

`/app/spaces/[spaceId]` 从占位页升级为知识库文档管理页：

- 进入页面后先沿用现有认证保护，再加载该空间的文档列表。
- 页面提供单文件选择控件、支持格式与 20MB 限制提示，以及上传中禁用状态。
- 上传成功后刷新列表；上传失败时显示后端统一中文错误消息。
- 列表展示文件名、格式、大小、上传时间、状态标签与删除操作。
- `failed` 状态可展示业务错误消息；其余状态仅显示标签，不伪造索引进度。
- 删除成功后刷新列表；失败时保留当前列表并显示统一中文错误。

前端继续通过既有 `apiRequest` 发送 `credentials: "include"` 请求。页面不读取或持久化 JWT，不显示 `storage_path`，也不绕过后端访问控制。

## 测试与验收

后端按 TDD 先补测试，至少覆盖：

- 未认证访问被拒绝。
- 上传时的空间所有权、跨用户和跨空间隔离。
- 支持格式、20MB 限制与空文件校验。
- 成功上传后文件与文档元数据均存在，列表按时间倒序返回。
- 响应不泄露所有权、知识库或存储路径字段。
- 删除同时处理元数据和本地文件；跨用户删除返回 `DOCUMENT_NOT_FOUND`。
- 错误响应保持统一中文 `{ error: { code, message, details } }` 结构。

前端至少覆盖：

- 新空间文档管理路由存在且未登录用户遵循既有跳转规则。
- 选择、上传中、成功刷新与失败提示交互。
- 文档状态标签和失败信息渲染。
- 删除成功后的列表刷新和失败提示。

集成验收需要真实 Docker PostgreSQL、后端和前端服务可用时才执行。若环境未启动或不可用，记录为未执行；单元测试、类型检查和构建不能替代 Cookie 会话与凭据型 CORS 的浏览器联调。

## 完成标准

- 当前用户能在自己的空间上传合规文件、查看上传记录并删除自己的记录。
- 文档记录和本地文件均不跨用户或跨空间泄露。
- 违规文件获得统一中文错误，且不留下孤儿文件或记录。
- V0.3 可以在不修改 V0.2 公共文档接口的前提下接入真实索引状态流转。
