# V1.0 轻量 GitHub 展示材料设计

## 目标

将 JPFX 包装为一个可信、可理解、可本地复现的 GitHub 项目，而不新增业务功能、不要求公开 Demo，也不引入示例账号或公共模型额度。

读者应能在 README 中快速回答四个问题：项目解决什么问题、核心流程是什么、当前已经实现到哪里、如何安全地在本地启动和验证。

## 已确认范围

本轮仅交付展示材料：

- 重构 README 的叙事与启动指引；
- 一张静态架构图；
- 4–6 张从真实本地页面采集的截图；
- 明确的验证证据、外部 Provider 与部署边界；
- 部署准备说明，而非实际部署。

本轮不做：

- 公开线上 Demo、Vercel/Render/Supabase 实际发布；
- 新增示例空间、示例用户、示例报告或伪造分析结果；
- 修改分析、RAG、报告、认证、导出等业务逻辑；
- 读取、复制、提交或展示 `.env`、Cookie、Token、数据库连接串或 Provider 密钥；
- 使用 `npm audit fix` 或升级依赖来处理既有审计项。

## 展示叙事

项目以“AI 产品经理的可追溯竞品研究工作台”为主线，不把它表述为通用聊天机器人或已上线 SaaS。

核心流程固定为：

```text
产品空间 → 私有资料 / RAG → 竞品分析任务 → 证据与报告归档 → PDF / DOCX 导出
```

README 将明确区分：

| 类别 | 表述原则 |
| --- | --- |
| 已实现 | 仅描述已有代码、测试或本地浏览器验收支持的能力。 |
| 已验证 | 列出对应命令与真实本地验收范围。 |
| 未验证 | Docker、外部 Provider、部署、视觉适配等单独标注。 |
| 未来工作 | 使用路线图表述，不暗示已经交付。 |

## README 信息架构

README 采用以下顺序，读者无需先读代码即可理解项目：

1. 一句话定位与价值主张；
2. 核心能力清单与研究流程图；
3. 架构图与技术栈；
4. 页面预览截图；
5. 本地启动前置条件和安全配置说明；
6. 可复现验证命令与结果边界；
7. Provider、部署和公开 Demo 状态；
8. 路线图与贡献/许可证入口（仅在现有仓库具备对应信息时加入）。

启动说明只引用 `.env.example` 和变量名称。任何密码、JWT、API Key 与真实连接信息由读者自行创建，README 不给出可用凭据。

## 架构图

架构图应为一个静态、可版本控制的 Mermaid 图，包含：

- 浏览器中的 Next.js 前端；
- FastAPI API 与 httpOnly Cookie 会话；
- PostgreSQL + pgvector；
- 本地 storage / 未来 Supabase Storage；
- DashScope、Bocha、DeepSeek 等可选外部 Provider；
- 报告与 PDF/DOCX 导出。

外部 Provider 节点必须标注为“用户配置后调用”，避免读者误解为仓库自带可用额度。

## 截图策略

截图只来自真实本地 UI，优先展示信息层级和已实现入口，不要求填充伪造业务数据。

建议素材：

1. 登录或注册页；
2. 已登录后的工作台/空状态；
3. 产品空间资料页面；
4. 分析任务入口或状态页面；
5. 报告中心或报告详情；
6. 模型设置页的脱敏状态。

截图前应清除可识别邮箱、Cookie、密钥、文件绝对路径与浏览器扩展信息。没有真实完成的页面不使用占位截图冒充完成结果。

## 验收标准

- README 可以独立解释产品、架构、启动方式和验证边界；
- 架构图能表达前端、API、数据库、Provider 与导出的关系；
- 所有截图均来自真实页面且不含敏感信息；
- 不声称公开 Demo、真实 Provider 调用或生产部署已经完成；
- 文档变更不影响前后端现有门禁；
- Git diff 不含 `.env`、截图中的凭据或无关依赖文件。

## 后续阶段

仅在轻量展示材料完成且用户明确需要时，才另行设计公开部署或受控示例数据方案。两者属于独立决策，不包含在本设计中。
