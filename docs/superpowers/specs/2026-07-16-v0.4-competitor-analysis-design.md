# V0.4 竞品分析任务与报告设计

## 目标与边界

V0.4 将现有的产品空间、私有资料和 RAG 检索串成真实的竞品分析闭环：用户创建任务，平台基于公开网页证据补充候选竞品，选择或自动确定最多三个竞品后生成可追溯的在线报告，并从同一结构化数据导出 PDF 与 Word。

本版本不做 OCR、超过三个竞品的批量分析、Redis、独立 Worker、队列、浏览器自动化抓取或定时监控。

## 已锁定的产品决策

- 任务输入为行业、产品方向、关键词，以及可选的 0–3 个已知竞品。
- 已知竞品不是必填项。用户可以跳过，交由系统从公开搜索证据中自动选择最多三个候选。
- 即使用户输入已知竞品，系统也必须通过公开搜索补充候选与证据；最终分析对象最多三个。
- 用户可以从候选中手动选择 1–3 个，或跳过确认步骤，系统自动选择证据充分的最多三个。
- 用户在设置页配置自己的 DeepSeek Key。Key 仅在后端加密保存和使用，不会在前端、日志、响应或测试夹具中出现。
- Bocha Key 是平台侧配置，仅从后端环境读取；前端不读取、保存或传递该 Key。
- 任务采用进程内轻量后台执行和前端轮询，不引入 Redis、独立 Worker 或队列。
- 报告在线展示，所有结论都需标记为“公开网页证据”“私有知识库证据”或“模型推断”。
- PDF 与 DOCX 导出均为 V0.4 范围，且从同一份结构化报告数据生成。

## 用户流程

1. 用户进入空间工作台，创建竞品分析任务，填写行业、产品方向和关键词；可选填写 0–3 个已知竞品。
2. 服务端验证当前用户对空间的归属，创建状态为 `draft` 的任务；前端进入候选确认页。
3. 服务端基于任务输入和已知竞品调用 Bocha 搜索，保存候选的名称、说明与公开网页证据。候选不足或搜索不可用时给出统一中文错误，不伪造证据。
4. 用户选择 1–3 个候选，或点击“系统自动选择”。自动选择只从已保存公开证据的候选中取最多三个。
5. 用户启动任务后，状态依次进入 `queued`、`running`。前端轮询任务详情，展示当前阶段和错误信息。
6. 运行过程检索当前用户、当前空间内的已索引私有资料，收集公开网页证据，调用该用户配置的 DeepSeek 模型生成结构化报告。
7. 成功后任务为 `completed` 并生成报告；失败后为 `failed`，保留安全的中文失败原因，用户可显式重试。
8. 用户在线查看报告、证据归因及来源；可下载 PDF 或 DOCX。下载和报告读取都受 `user_id + space_id` 隔离。

## 状态与执行模型

任务只允许以下状态：`draft → queued → running → completed / failed`。`failed` 允许显式重试，重试会重新进入 `queued`；`running` 不允许重复启动或重试。

创建候选属于 `draft` 阶段，不启动完整分析。启动分析时先校验：已有 1–3 个最终竞品、用户存在可用的 DeepSeek 配置、任务仍属于当前用户与空间。任一步失败都使用统一错误响应：

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "中文错误消息",
    "details": {}
  }
}
```

后台调用只持有任务 ID；每个服务步骤重新按 `user_id + space_id` 读取数据。进程重启后未完成任务不承诺自动恢复，仍由用户显式重试；这与不引入队列的范围一致。

## 数据模型

新增或扩展的持久化模型均包含所有权字段与必要索引：

- `model_configs`：`user_id`、provider、加密后的 Key、Key 掩码、默认模型、启用状态和时间戳。响应只返回掩码和配置状态，不返回明文或密文。
- `analysis_tasks`：`user_id`、`space_id`、任务标题、行业、产品方向、关键词、已知竞品、最终竞品、选择模式、状态、失败原因、阶段和时间戳。
- `competitor_candidates`：任务归属、名称、简介、来源方式、选择状态与排序。自动补充候选必须至少关联一条公开证据。
- `task_evidence`：任务或候选归属、`web / private_knowledge / model_inference` 类型、标题、URL、文档/切片引用、摘录和时间戳。
- `competitor_reports`：`user_id`、`space_id`、`task_id`、标题、结构化 JSON、版本与时间戳。报告正文由结构化 JSON 渲染，不以单独 Markdown 作为导出真源。

数据库外键与查询必须阻止跨用户、跨空间关联；候选、任务证据和报告均不能绕过任务的所有权边界。

## 服务与 Provider 边界

- `DeepSeekProvider`：使用用户的已解密 Key 调用兼容 Chat Completions 的接口。Provider 层绝不记录授权头、Key 或完整敏感请求。
- `BochaSearchProvider`：仅使用后端环境 Key，返回可审计的标题、URL、摘要和检索时间。搜索失败映射为统一中文错误。
- `CandidateDiscoveryService`：形成查询、去重候选、保存公开证据；不允许模型无证据地确认自动候选。
- `AnalysisRunService`：编排固定顺序的私有知识检索、公开资料整理、分析与报告组装；不构建自治 Agent。
- `ReportExportService`：将同一报告 JSON 渲染为 HTML/PDF 与 `.docx`，保留标题、竞品对比、结论、证据标签与链接。

报告生成时，私有知识检索沿用 V0.3 的 `user_id + space_id + indexed` 过滤；公开证据不得被写入私有资料库。模型推断必须与可引用事实分开存放和展示。

## API 契约

- `GET /api/v1/model-configs/deepseek`：读取当前用户的安全配置摘要。
- `PUT /api/v1/model-configs/deepseek`：创建或更新 DeepSeek Key；写入后只返回已配置状态和掩码。
- `POST /api/v1/spaces/{space_id}/analysis-tasks`：创建草稿任务。
- `POST /api/v1/analysis-tasks/{task_id}/candidates/discover`：基于公开搜索补充候选与证据。
- `PUT /api/v1/analysis-tasks/{task_id}/competitors`：手动选定 1–3 个最终竞品。
- `POST /api/v1/analysis-tasks/{task_id}/competitors/auto-select`：自动选定有证据的最多三个。
- `POST /api/v1/analysis-tasks/{task_id}/run`：排队并启动分析。
- `GET /api/v1/analysis-tasks/{task_id}`：供详情页轮询任务状态、阶段和安全错误信息。
- `POST /api/v1/analysis-tasks/{task_id}/retry`：仅重试失败任务。
- `GET /api/v1/spaces/{space_id}/reports`、`GET /api/v1/reports/{report_id}`：读取隔离的报告和证据。
- `GET /api/v1/reports/{report_id}/export/pdf`、`GET /api/v1/reports/{report_id}/export/docx`：生成并返回受保护的文件下载。

所有受保护接口使用既有 Cookie 会话；浏览器请求继续使用 `credentials: "include"`，且 CORS 保持精确 origin 与 `allow_credentials=True`。

## 前端体验

- 设置页提供 DeepSeek 配置表单，输入框仅用于提交；保存后显示掩码和“已配置”，不回填明文 Key。
- 创建任务页展示输入说明、已知竞品标签输入与“可跳过，系统将自动发现”的明确提示。
- 候选确认页将每个候选与公开证据并列呈现，支持手动选择或系统自动选择；未达到 1 个有效候选时不能启动。
- 任务详情页显示 `queued/running` 阶段进度，轮询在完成或失败后停止；失败提供重试按钮。
- 报告详情页按竞品、结论、对比表和建议组织内容，并在每条信息旁清晰展示证据类型；提供 PDF、Word 导出入口。
- 未登录访问受保护页面跳转 `/login`；接口未授权时保持既有登录跳转行为。

视觉方向沿用已确认的深色工作台：左侧导航、顶部任务上下文、阶段进度、竞品对比卡、报告表格和证据面板。视觉效果不替代前端可访问性与状态反馈要求。

## 错误与安全规则

- 未配置或无法解密 DeepSeek Key 时，任务不得运行，返回中文配置错误；不得使用伪造模型结果。
- Bocha 未配置、搜索失败、无可用候选、模型上游失败、报告渲染失败均记录安全失败原因并返回一致错误契约。
- Key 加密密钥仅来自后端环境；应用启动时缺失则拒绝启用配置写入，不回退到明文存储。
- 日志、数据库响应、前端状态、导出文件和测试夹具均不得包含 DeepSeek Key、Bocha Key、Cookie、Token 或数据库连接串。
- 导出端点直接按报告的 `user_id + space_id` 校验，不依赖前端隐藏按钮作为访问控制。

## 测试与验收

后端采用 TDD，至少覆盖：

- DeepSeek Key 的加密存储、掩码响应、未配置与解密失败；
- Bocha Provider 的 MockTransport 成功、失败与无 Key 场景；
- 任务、候选、证据、报告和导出的用户/空间隔离；
- 已知竞品 0–3 校验、候选证据要求、手动与自动选择、最多三个限制；
- 状态转换、重复运行拒绝、失败持久化与显式重试；
- 私有检索过滤、证据类型标注、结构化报告写入；
- PDF/DOCX 的授权、内容来源和文件响应；真实第三方调用不进入自动测试。

前端至少覆盖：

- 设置页不回显 Key，配置请求保持 Cookie；
- 创建任务表单和 0–3 已知竞品校验；
- 候选证据展示、自动选择和最多三个选择限制；
- 任务轮询、完成停止、失败重试与未授权跳转；
- 报告证据标签及 PDF/Word 导出请求。

最终门禁包括后端 Pytest、Ruff 与格式检查，前端 test、路由检查、TypeScript、lint、build、audit，以及可用环境下的 Docker PostgreSQL 集成验证。真实 Bocha/DeepSeek 调用只在用户自行配置 Key 且明确允许时执行。
